# 目标与业务原则

## 1. 工具要解决什么问题

业务人员每周维护 Shark / Ninja 项目周报。周报适合汇报，但不适合长期结构化管理；Airtable 用于持续管理项目、SKU、任务、问题和负责人；All Tracker 是管理层查看大节点、日期和简要备注的汇总表。

工具的职责是把三者连接起来，同时防止以下错误：

- 将周报写到错误项目或错误 SKU。
- 把旧周报覆盖到新数据上。
- 重复导入时重复追加相同进展或创建重复任务。
- 把人员、工厂、选项或日期猜错后写入。
- All Tracker 回写时覆盖 Airtable 中更新过的内容。
- 网络返回不确定时盲目重试，造成重复记录。

## 2. 已确认的业务权威顺序

### 正常主流程

1. 周报是每周项目更新的主要来源。
2. 周报导入 Airtable 后，Airtable 成为结构化管理平台。
3. Airtable 输出 All Tracker，All Tracker 只展示管理需要的大节点、日期和简要 Remark。
4. All Tracker 回到 Airtable 不是日常主同步，只用于复验、查漏和人工审核后的有限修正。

### 冲突时的原则

- 周报与 All Tracker 的正式项目编号优先于 Airtable 中人工临时编写的编号。
- `X` 开头的编号是临时编号，不能当成正式来源编号。
- 正常情况下不应让 All Tracker 全量覆盖 Airtable。
- All Tracker 回写必须以此前从 Airtable 导出的基线为前提，发现云端和本地同时修改时停止覆盖。

## 3. Project 与 SKU 的管理边界

业务最终原则：

- 周报本身只有 Project 维度，没有可靠的 SKU 级任务或问题维度。
- 周报中的 Current Progress、Task、Issue 都属于整个 Project。
- SKU 维度从 Airtable 开始建立和维护。
- 同一个 SKU 可能对应不同工厂，因此 Airtable 的 SKU 管理单元必须区分工厂。
- 不能仅凭 SKU 匹配，也不能把项目级周报内容无判断地复制成多份 SKU 内容。

当前实现与该原则尚有差距：

- 当前 `source/autopm/identity.py` 使用“正式项目编号 + SKU + 唯一工厂”定位 Airtable `Projects` 记录。
- 当前 `source/autopm/sync.py` 会把一个来源项目复制成每个匹配到的 SKU/工厂记录，再处理 Project 字段、Task 和 Issue。
- 这能阻止跨 SKU 写错，但可能把项目级进展、任务或问题重复挂到多个 SKU 管理记录。

下一阶段必须先明确 Airtable 中“Project 父级”和“SKU/工厂管理单元”的数据模型，再重构写入归属。这个差距是业务 P0，不是普通优化。

## 4. All Tracker 的定位

All Tracker 是 Dashboard，不承担 Airtable 的全部细节：

- 重点展示项目基本信息、大里程碑和关键日期。
- Remark 可记录少量项目进展或小问题。
- 不要求展示所有 Tasks、Issues、Issue Actions 和完整历史。
- 公式列、空白值和未明确映射的字段不能借回写流程清空云端内容。

本工具中的“本地 All Tracker Excel”与 Airtable 内名为 `ALL Tracker` 的表不是同一个对象。当前主功能维护本地 Excel 副本，不会把本地总表静默写进 Airtable 的 `ALL Tracker` 表。

## 5. 完成的定义

一次安全导入至少应满足：

1. 源文件、报告日期和项目编号可追溯。
2. 目标 Base、表、字段 ID 和字段类型已经重新核对。
3. 项目身份唯一，不用名称或模糊相似度猜测。
4. 写入前有逐字段预览和阻断/提示清单。
5. 写入前重新读取目标记录，确认身份和版本未变化。
6. 写入后重新读取，确认实际值等价。
7. 重复运行不产生额外变化。
8. All Tracker 回写有导出基线，并执行三方冲突检测。

目前技术保护大多已实现，但 Project/SKU 归属模型仍未完成业务闭环，因此当前版本应视为可测试的候选版本，不应标记为最终业务验收。

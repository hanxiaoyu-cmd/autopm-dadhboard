# 接手开发顺序

## 第 0 步：建立可复现环境

1. 阅读本交接 README、业务原则、匹配规则和已知问题。
2. 从 `source/` 启动程序，不先修改真实 Airtable。
3. 运行全量测试并保存结果。
4. 准备脱敏周报、All Tracker 和 Airtable snapshot fixture。
5. 只读获取当前 Base schema，确认字段 ID、类型、Link 目标和 Select 选项没有漂移。

验收：源码可启动；全量测试结果明确；测试输入不含生产凭据。

## 第 1 步：修复 All Tracker `time` 序列化故障

rc5 已完成源码修复、7 项新增回归和用户本轮指定总表的导出验证；历史 V2 原文件未在本轮复测。当前证据与范围见 [更新日志](../CHANGELOG.md)，下方保留原验收要求。

范围只应包含：

- `tracker.scalar/read_tracker` 的稳定 JSON 值处理。
- 日期列纯时间的明确诊断。
- 最小回归测试。

验收：

- `All Projects Tracker V2 (1).xlsx` 可生成预览。
- `AC695` 不被猜成某个日期。
- 其他日期、公式、内容哈希和回写基线不回归。

## 第 2 步：确认并实现 Project/SKU 数据模型

这是下一阶段的核心任务。开发前需与业务确认：

1. Airtable 中哪个记录代表整个 Project。
2. SKU + 工厂记录是否继续放在 Projects 表，还是迁移到 Project SKUs/其他子表。
3. Task/Issue 的 Project Link 应指向哪个层级。
4. Project 字段如何在多个 SKU 行中展示而不重复写入。
5. All Tracker 一行粒度是 Project 还是 Project + SKU + 工厂。

完成后重构：

- 第一层按正式项目编号匹配 Project。
- 第二层仅对 SKU 专属字段按 SKU + 工厂匹配管理单元。
- Current Progress、Task、Issue 只处理一次并归属 Project。
- 不用 SKU 推断周报中没有表达的归属。

验收场景必须至少覆盖：

- 一个 Project 一个 SKU 一个工厂。
- 一个 Project 多 SKU 同工厂。
- 一个 Project 同 SKU 多工厂。
- 一个 Project 多 SKU 多工厂。
- Airtable 仅有 X 临时记录。
- 正式记录与 X 临时记录并存。
- 周报缺 SKU，但 Project 编号有效。

## 第 3 步：统一 Project 与 Task 的里程碑权威

需要确认 Project 直接日期与 Task Due Date 的关系：

- 哪些日期只存 Project。
- 哪些日期只存 Task。
- 哪些为兼容字段，需要双写但指定单一权威。
- Airtable -> All Tracker 从哪一侧取值。
- All Tracker 回写修改哪一侧，以及另一侧如何保持一致。

不要让两个字段互相覆盖形成循环。

## 第 4 步：完善可用性和错误提示

- 报错必须包含文件、工作表、单元格/项目、语义字段和处理结果。
- 将“云端读取成功、本地文件失败”与“Airtable 网络失败”分开显示。
- 预览清楚区分阻断、跳过、警告和已写入但回读未验证。
- 对纯时间、错误日期、重复表头、范围过大和公式列给出可操作建议。

## 第 5 步：端到端验收

至少验证：

1. 周报 -> Airtable 预览。
2. 经批准的小范围测试写入。
3. 写后回读。
4. 同文件重复导入为 0 变化。
5. Airtable -> All Tracker 导出。
6. 未编辑副本回写为 0 变化。
7. 修改一个 Project 字段和一个 Task 日期后回写。
8. 再次回写为 0 变化。
9. 云端和本地同时修改时阻断。
10. 多 SKU/工厂项目不重复创建项目级 Task/Issue。

## 第 6 步：发布

- 更新 `source/autopm/__init__.py` 版本。
- 更新 `source/README.md`。
- 全量测试通过后再打包。
- 在无 Python PATH、空白设置和公司网络环境分别验证。
- 检查构建物不包含凭据和业务数据。
- 发布说明写明已验证范围和未验证边界。

## 不应继续使用的捷径

- 用项目名称模糊匹配。
- 选择多个候选中的第一条。
- 自动创建 Airtable 选项、人员或工厂。
- 没有 `.autopm.json` 基线就允许 All Tracker 回写。
- 将空白单元格理解为清空云端。
- 网络超时后直接重复 POST。
- 用全部 SKU 复制项目级任务和问题。
- 把测试通过等同于业务验收或生产部署成功。

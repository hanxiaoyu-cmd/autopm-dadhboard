## 2. 已完成的重要修复

### TLS 证书不受信任

公司浏览器能访问 Airtable，但早期程序使用的证书来源不兼容企业 HTTPS 代理。修复后使用系统 ROOT/CA，并保留完整 TLS 验证。

### 新电脑映射缺失

只为确认的主 Base 提供非敏感默认映射，例如 Engineering Remark 版本存储、Task/Issue 项目 Link 和 Factory code。其他 Base 不套用固定 ID。

### 富文本写入成功却误报失败

Airtable 会重排 Markdown 有序列表编号并增加尾部换行。旧程序逐字比较后报告失败，用户重试又可能重复追加。rc4 在共享比较和合并路径中只规范列表标记格式，正文变化仍会被发现。

## 4. P0：业务模型尚未闭环

业务要求周报内容按 Project 管理，SKU 维度从 Airtable 开始。当前代码却先用编号 + SKU + 工厂把来源项目展开到管理单元，再写 Project/Task/Issue。

风险：同一 Project 有多个 SKU/工厂时，项目级内容可能重复或挂到错误层级。

必须完成：

1. 确认 Project 父对象或 Project Group 的唯一身份。
2. 明确哪些字段属于 Project、哪些属于 SKU/工厂单元。
3. Task/Issue 只关联 Project 层，不因 SKU 数量复制。
4. All Tracker 仍按 Project Dashboard 展示，SKU 行只作为展示或单位绑定。
5. 增加同 Project 多 SKU、多工厂的验收用例。

## 5. 已修复：All Tracker 纯时间值导致预览失败（rc5）

2026-09-21 诊断结论：

- Airtable 网络请求成功，故障发生在生成本地总表预览时。
- 文件：`All Projects Tracker V2 (1).xlsx`。
- 单元格：`ALL PROJECTS!AC695`，列标题 `FOT`。
- openpyxl 读取类型：`datetime.time`，值为 `00:00:15.231000`，单元格显示格式为日期 `dd-mmm-yy`。
- 该行 `Project Number` 为空，是一个落在有效读取范围内的异常/游离值。
- `source/autopm/tracker.py::scalar()` 只处理 `datetime` 和 `date`，随后 `read_tracker()` 对所有非公式值执行 `json.dumps` 计算内容哈希，触发 `Object of type time is not JSON serializable`。
- 同目录其他四个主要 All Projects Tracker 文件没有 `time` 值，`read_tracker()` 可正常完成。

2026-09-21 修复内容：

1. `scalar()` 将 `datetime.time` 转为 ISO 文本、`timedelta` 转为保留跨天和微秒的稳定文本；沿用已有完整日期处理及指纹结构。
2. 日期语义列中的时间／时长给出工作表、坐标和表头警告，导出预览与回写预览均保留该诊断，不推测日期。
3. 未修改格继续复制原始 XML；若云端有效完整日期更新一个纯时间格式格，仅将该目标格改为完整日期格式。
4. 新增 7 项合成回归，覆盖孤立行、有效项目行、精度、指纹、原生 XML、旁路审计、回写基线和日期显示格式。

本轮在隔离的原始提交上复现序列化错误，再在修复版通过全部用例。用户本轮指定的总表可正常读取，使用本轮只读取得的 Airtable 快照生成副本并更新 406 个单元格；原表保持不变，19,505 个公式保留，再次导出和未编辑回写预览均为 0 变更。上述历史 V2 原文件本轮未提供，未声称对它重新实测。详见 [更新日志](../CHANGELOG.md)。

## 6. 其他已知差距

- Project 表和 Task 表可能同时保存部分里程碑日期，双处日期的最终权威和同步策略仍需确认。
- All Tracker 只覆盖部分项目字段和大里程碑，不是 Airtable 全量镜像。
- 隐藏在 Excel 超链接目标中的 URL 仍可能无法被本地解析器读取。
- 未明确的人员、工厂、日期、Select 选项和重复任务继续以提示或跳过处理。
- DeepSeek 解析质量不能代替身份、字段、日期和目标记录验证。
- 历史 `legacy-reference/` 使用项目名称匹配，与当前严格规则不同，不应恢复为生产路径。

# 周报工具：目标与当前实现核对

审查日期：2026-09-19。对象：`D:\个人资料\AI学习圈\SN Auto PM\weekly_importer\weekly_importer` 下的 10 个 Python 模块。

**结论：当前独立版本不能满足此前讨论的完整周报工具目标。它主要是“从 All Tracker 按项目名称追加工程备注”，附加简化导出、Excel 回写及历史清理功能；即使只按这个较小范围验收，也有写错对象、清空字段和丢失历史的风险。**

## 1. 这个工具是干什么的

把每周 Shark/Ninja 原始周报里分散的项目进展、时间节点和问题，转成 AutoPM 可以持续跟踪的数据，减少人工在周报、Airtable 和本地总表之间重复抄写。

完整目标包含三类信息：

- **Projects：** 项目身份、工程进展、当周更新、阶段及已确认需要维护的项目字段。
- **Tasks：** 时间线中的任务/里程碑、截止日期，以及有明确证据的负责人和完成信息。
- **Issues：** 周报中的问题、行动和责任人。

之后从已确认的云端数据维护本地 All Tracker。不能因为某列空白就清掉已有数据；不能混淆同名项目；不能让旧周报倒灌最新状态；同一份文件反复导入不应产生重复内容或记录。

这是依据此前需求恢复的完整目标。**当前 README 自己声明的范围更小：只读 ALL Tracker，更新 Projects 工程备注。** 范围差异与代码缺陷需要分别看待。

## 2. 应当怎么做

1. **识别原始周报。** 定位 Report 页及项目区块，提取文本、日期和必要的格式信息，保留文件、页、单元格等来源。
2. **整理为项目、任务、问题。** 用 Project ID 精确找项目；有多个候选或来源不清楚的，列入待处理，不能默认挑一条。
3. **生成可核对的差异。** 读取 Airtable 当前字段结构和数据，展示“哪个记录、哪个字段、原值、新值、来源、跳过原因”。普通空白不代表删除，历史日期不代表任务已经完成。
4. **执行增量更新并验证。** 写前检查数据是否被他人改动；按约定维护历史，重复运行保持一致；保存成功、失败和待确认清单，写后回读核对。
5. **维护本地总表。** 保护人工维护内容、公式和基线。若要从总表反向修改云端，必须另有明确字段范围和真正的冲突检测，不能只比较当前两个值。

此前确认过的具体映射包括：工程进展对应 Engineering remark(Manual)，Eng Update This Week 对应 Current stage，时间线日期对应 Tasks 的 Due Date，LOA 保留完整文本。这些是历史需求依据；本次没有重新连接线上核验 schema，后续实现前仍要核对实际字段及类型。

## 3. 当前代码做到了什么

| 能力 | 当前实际表现 | 判断 |
|---|---|---|
| 读取原始 Shark/Ninja 周报 | 固定按第 2 行表头读取 All Tracker 三列；真实 Shark 样本还会选错工作表 | 不满足原始输入要求 |
| 识别项目 | 按项目名称精确匹配，重名覆盖前一条 | 不满足 Project ID 唯一匹配 |
| 项目更新 | 只写工程备注 | 部分实现 |
| 时间线 Tasks、Issues | 导入链没有相应解析及写入 | 未实现 |
| 重复导入 | 简单相同内容第二次不写；整段历史往返会嵌套 | 仅简单场景通过 |
| 预览 | 返回数量，没有逐条前后差异 | 不足以审批具体修改 |
| 本地 All Tracker | 新建简化十列表，仅填主要五列 | 不是维护原有完整总表 |
| Excel 回写及冲突检测 | 没有导出原值快照，空值也生成清空操作 | 存在数据风险 |

还有两个不宜忽略的观察：预览不返回记录级差异；字段名、类型和可写性没有在实际导入前完整校验。GUI 虽有“自动识别项目、任务与问题”的文案，实际主流程只传入工程进展。

## 6. 下一步的最小实施顺序

1. 以完整周报目标确定主实现，先对照已有完整导入器复用原始周报解析与字段映射；不要直接在这个备注导入器上重复造一套。
2. 先修会写错、清空或丢历史的路径，以及写后报错问题；修复前不要用当前回写/清理功能处理正式数据。

## 二、核心产品：Ody平台

### 2.1 产品定位

Ody是Rodyr的旗舰产品，定位为"团队知识运行时"(knowledge runtime for teams)。

**核心价值主张**:
> "观察团队实际工作方式（编码会话、Slack线程、PR、调用），将稳定部分蒸馏成版本化、可被Agent调用的Skills，包含类型化输入和证据追踪，从每次运行中学习。"

### 2.2 技术架构

```

│                      Ody 架构                               │
├─────────────────────────────────────────────────────────────┤

│  │ Slack   │ Notion  │ Linear  │ GitHub  │ Gmail   │       │
│  │ Conflu. │ Jira    │ G.Drive │ Teams   │         │       │

│       │         │         │         │                      │
│       ▼         ▼         ▼         ▼                      │
│  ┌─────────────────────────────────────────────────┐       │
│  │         知识图谱 (Knowledge Graph)                │       │

│  └──────────────┬──────────────────────────────────┘       │
│                 │                                        │
```

### 2.3 技术栈

| 组件 | 技术选择 |
|------|----------|
| **主要语言** | TypeScript (92.3%), Shell (5.1%), Python (2.1%) |
| **LLM支持** | OpenRouter, OpenAI, Anthropic, Ollama, Groq |
| **Embedding** | Transformers, Ollama, OpenAI, Cohere |
| **协议** | MCP (Model Context Protocol) |
| **存储** | SQLite (本地) |
| **部署** | On-premise优先，支持自有LLM |

**核心技术能力**:
- ✅ 自适应RAG（检索增强生成）
- ✅ Agentic知识图谱
- ✅ MCP协议集成
- ✅ 多源知识连接器
- ✅ 矛盾检测与漂移分析
- ✅ CI/CD集成能力

### 2.4 主要功能模块

1. **Capture (捕获)**: 从Slack、Notion、Linear、GitHub等自动捕获团队决策
2. **Answer (问答)**: 200ms内返回带引用的答案，支持MCP调用
3. **Compound (编译)**: 从实际行为中自动编译Runbook，支持版本追踪

### 2.5 开源核心 (ody-refine)

已在GitHub开源核心模块:
- **许可**: Apache 2.0
- **定位**: 文档矛盾检测与修复工具
- **包结构**: monorepo设计，模块化发布

## 四、AI能力评估

### 4.1 自研vs套壳

| 维度 | 评估 |
|------|------|
| **模型层** | 套壳 - 使用OpenRouter/OpenAI/Ollama等第三方LLM |
| **RAG层** | 自研 - 自适应RAG知识图谱 |
| **Agent框架** | 集成MCP协议 + 自研Skills运行时 |
| **检测引擎** | 自研 - 矛盾检测、漂移分析、过期检测 |
| **结论** | **核心能力是自研的，但底层依赖第三方LLM** |

### 4.2 能力亮点

✅ **优势**:
- 自适应RAG知识图谱设计合理
- MCP协议深度集成（Claude Code、Cursor、Codex）
- 开源核心模块验证了技术可行性
- 内部基准显示"agent-with-Ody beating agent-alone"

⚠️ **局限**:
- 没有自研大模型能力
- 知识图谱的智能化程度取决于使用的LLM
- 产品仍在MVP阶段，未经大规模验证

### 4.3 与AutoPM需求的匹配度

## 九、最终建议

### 9.1 合作适合度评估

| 评估维度 | 评分 | 权重 | 加权得分 |
|----------|------|------|----------|
| AI技术能力 | 6/10 | 25% | 1.5 |
| 企业级产品能力 | 3/10 | 20% | 0.6 |
| 团队规模与稳定性 | 2/10 | 15% | 0.3 |
| 行业经验(制造业) | 2/10 | 15% | 0.3 |
| 集成能力 | 3/10 | 15% | 0.45 |
| 商业成熟度 | 3/10 | 10% | 0.3 |
| **总分** | | 100% | **3.45/10** |

### 9.2 建议结论

**Rodyr目前不适合作为AutoPM开发的唯一主要合作伙伴，但可以作为技术咨询或特定模块的专项承包商。**

### 9.3 具体建议

#### ✅ 可采用的方式

1. **技术咨询角色**: 邀请Ufuk作为AutoPM AI能力的外部技术顾问，按小时付费
2. **特定模块开发**: 将Ody的知识管理能力（Skills运行时）作为AutoPM的子系统采购
3. **POC验证**: 先进行小规模概念验证(3-6个月)，评估技术价值后再决定

#### ❌ 避免的方式

1. **独家深度绑定**: 不建议给予排他性合作权
2. **大规模投资**: 在产品成熟度验证前，避免大额投资或收购
3. **核心系统依赖**: AutoPM的核心系统建设不应依赖Rodyr的持续运营

#### 🔧 如果决定合作，建议

| 阶段 | 行动项 | 风险控制 |
|------|--------|----------|
| 短期(1-3月) | 签署NDA，明确IP归属 | 保护SharkNinja的技术资产 |
| 中期(3-6月) | POC项目，验证3-5个Feature Cards | 设定明确的验收标准 |
| 长期(6-12月) | 根据POC结果决定合作深度 | 保留退出选项 |

## 十、关键发现汇总

### 🔴 高风险项
1. 公司成立于2025年，历史不足1年
2. 团队规模极小，无完整组织架构
3. 无制造业或消费电子领域客户案例
4. 创始人缺乏企业级产品交付经验

### 🟡 中风险项
1. 定价和商业模式不透明
2. 缺乏Oracle ERP、SharePoint等企业系统集成能力
3. 产品处于MVP阶段，未经大规模市场验证

### 🟢 积极项
1. 创始人技术背景扎实，有RAG/AI实战经验
2. MCP协议集成与AutoPM的AI能力需求匹配
3. On-prem部署能力满足企业安全要求
4. 开源核心验证了技术可行性

## Step 1: 基础设施与部署 — "有地方跑"（INFRA）

### 1.1 服务器选型与申请

- **具体内容**: 确认公司现有云资源（AWS/Azure/阿里云）是否可复用；若无可用资源，走新申请流程，填写资源申请表，说明用途、规格需求、预估费用
- **天数**: 2天
- **角色**: DevOps / 后端工程师
- **依赖**: 无
- **风险等级**: 低
- **交付物**: 服务器实例已开通，SSH可登录，资源清单文档（IP、规格、有效期）

### 1.2 运行环境搭建

- **具体内容**: 在服务器上安装 Ubuntu 22.04 LTS（或公司标准OS）、Python 3.11+、Nginx、PostgreSQL 15+、Redis 7+；配置 Python 虚拟环境（venv/conda）；安装 Node.js 18+（前端构建用）；配置 systemd 服务管理
- **天数**: 2天
- **角色**: DevOps / 后端工程师
- **依赖**: 1.1 完成（服务器已开通）
- **风险等级**: 低
- **交付物**: 服务器环境就绪清单（`python --version`、`nginx -v`、`psql --version` 均可输出），虚拟环境已创建并验证

### 1.3 域名与内网访问配置

- **具体内容**: 申请内网域名（如 `autopm.internal.company.com`）；配置 Nginx 反向代理指向后端服务端口；配置 DNS 解析；若需外网访问则额外申请公网域名并配置 SSL 证书（Let's Encrypt 或公司证书）
- **天数**: 1天
- **角色**: DevOps / 后端工程师
- **依赖**: 1.2 完成（Nginx 已安装）
- **风险等级**: 低
- **交付物**: 域名可访问，`curl https://autopm.internal.company.com` 返回 200（或 Nginx 默认页）

### 1.4 自动部署流程

- **具体内容**: 搭建 Git 仓库（公司 GitLab/GitHub）；编写 `docker-compose.yml`（应用+数据库+Redis）；编写 CI/CD 脚本（`.gitlab-ci.yml` 或 GitHub Actions）：push main 分支 → 自动构建镜像 → 自动部署到服务器；配置环境变量管理（`.env` 文件，敏感信息不进仓库）
- **天数**: 1天
- **角色**: DevOps / 后端工程师
- **依赖**: 1.2 完成（运行环境就绪）
- **风险等级**: 低
- **交付物**: `git push origin main` 后 5 分钟内自动部署完成，可在服务器上 `docker ps` 看到 running 容器

### 1.5 服务器监控

- **具体内容**: 安装并配置监控工具（Prometheus + Grafana，或公司现有监控平台）；配置关键指标告警：CPU>80%、内存>85%、磁盘>90%、服务进程挂掉；配置告警通知渠道（邮件/企业微信/Slack）
- **天数**: 1天
- **角色**: DevOps / 后端工程师
- **依赖**: 1.2 完成（服务器可运行服务）
- **风险等级**: 低
- **交付物**: Grafana 面板可看到服务器状态，手动 kill 进程后 5 分钟内收到告警通知

**INFRA 合计**: 5-7天 | 1人 | 风险低 | 预计完成 5月19日

## Step 2: 数据管道 — "有数据吃"（DATA）

> **⚠️ 最大风险模块**: E3 是否有 API 是核心未知数，直接影响后续所有模块。本模块按三种场景分别拆解，优先推进场景确认。

### 2.1 E3 数据源对接方案

#### 2.1.1 E3 API 可行性调研

- **具体内容**: 联系 SharkNinja IT 部门或 E3 系统管理员，确认 E3 是否提供 API 接口；获取 API 文档（如有）；确认 API 调用权限申请流程和审批周期；验证 API 可获取的数据范围（项目列表、里程碑、状态、负责人、日期等）
- **天数**: 2天
- **角色**: 后端工程师 + IT对接人
- **依赖**: 无（越早启动越好，可与 INFRA 并行）
- **风险等级**: 极高
- **交付物**: 《E3 API 可行性调研报告》：结论为「有API/无API/部分API」，附接口清单或否定证据

#### 2.1.2 场景A — E3 有 API

- **具体内容**: 根据 API 文档编写 Python 数据拉取模块；实现 OAuth/API Key 认证；编写请求封装类（重试、超时、错误处理、速率限制）；拉取测试：调用 API 获取 10 条项目数据并写入本地 JSON 验证完整性
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 2.1.1 结论为「有API」
- **风险等级**: 中（API 可能限流或数据不全）
- **交付物**: `e3_api_client.py` 模块，`python -m e3_api_client --test` 成功拉取并输出 10 条项目数据

#### 2.1.3 场景B — E3 无 API，走 CSV 导出

- **具体内容**: 与 E3 使用者确认手动导出 CSV 的操作步骤和可行频率（每日/每周）；确定导出字段映射关系（E3 字段 → AutoPM 标准字段）；编写 CSV 解析模块（`csv_parser.py`），处理编码问题（中文乱码）、日期格式、空值、换行符等；配置文件上传入口：Web 页面或指定 SFTP 目录自动扫描
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 2.1.1 结论为「无API」
- **风险等级**: 中（依赖人工操作，可能遗忘导出）
- **交付物**: CSV 上传页面或 SFTP 自动扫描可用，上传示例 CSV 后系统正确解析并入库

#### 2.1.4 场景C — E3 无 API，走数据库直连

- **具体内容**: 确认 E3 底层数据库类型（Oracle/SQL Server/其他）；申请数据库只读账号（需 IT 审批，可能耗时 1-2 周）；确认可查询的表和视图（E3 可能是商业软件，底层表结构不透明）；编写 SQL 查询脚本，提取项目数据；验证查询性能（避免慢查询影响 E3 在线业务）
- **天数**: 5天（含审批等待）
- **角色**: 后端工程师 + DBA
- **依赖**: 2.1.1 结论为「无API」+ IT 审批通过
- **风险等级**: 高（审批可能被拒、表结构可能不开放、慢查询可能被禁）
- **交付物**: 数据库只读账号可用，SQL 脚本执行成功并输出 10 条项目数据，查询耗时 < 5秒

### 2.2 邮件数据解析

#### 2.2.1 邮件接入方案确认

- **具体内容**: 确认公司邮件系统类型（Exchange/Outlook 365/Gmail 企业版）；确认邮件自动读取的技术方案：Exchange Web Services (EWS) / Microsoft Graph API / IMAP；申请邮件 API 的应用注册和权限（需 IT 管理员审批）
- **天数**: 2天
- **角色**: 后端工程师 + IT对接人
- **依赖**: 无（可与 2.1 并行）
- **风险等级**: 中（审批可能延迟）
- **交付物**: 邮件 API 应用已注册，Client ID/Secret 已获取，权限已授予

#### 2.2.2 CC 邮件自动提取

- **具体内容**: 配置邮件监听规则：监听发往 AutoPM 专用邮箱的 CC 邮件，或按规则过滤（发件人/主题关键词）；编写邮件内容解析器：提取发件人、时间、主题、正文、附件；从邮件正文中提取项目状态关键词（如"delayed"、"blocked"、"need approval"等）；处理邮件线程（同一项目多封邮件的关联关系）
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 2.2.1 完成
- **风险等级**: 中（邮件格式不统一，解析准确率需迭代）
- **交付物**: `email_parser.py` 模块，输入 10 封测试邮件，输出结构化 JSON（项目ID、状态关键词、时间戳）

### 2.3 数据清洗与标准化

#### 2.3.1 字段映射表

- **具体内容**: 梳理 E3 原始字段 → AutoPM 标准字段的映射关系；梳理 PLM 原始字段 → AutoPM 标准字段的映射关系；处理字段名称不一致（如 E3 的 "Due Date" vs PLM 的 "Target Date"）；处理字段缺失的默认值策略（空值 → "未设定"、日期缺失 → null 等）；输出《字段映射表》文档
- **天数**: 2天
- **角色**: 后端工程师 + PM（业务侧确认）
- **依赖**: 2.1 场景确认后（知道 E3 能给什么数据）
- **风险等级**: 中（业务理解偏差可能导致映射错误）
- **交付物**: 《字段映射表》Markdown 文档，经 PM 确认签字

#### 2.3.2 数据清洗 Pipeline

- **具体内容**: 编写数据清洗模块 `data_cleaner.py`，实现以下清洗规则：日期格式统一（多种输入格式 → ISO 8601）；项目状态枚举标准化（"In Progress"/"进行中"/"WIP" → "IN_PROGRESS"）；负责人姓名去重与 ID 匹配（中英文名、别名统一映射）；重复项目检测与去重（基于项目编号+名称的模糊匹配）；异常值过滤（结束日期早于开始日期、里程碑日期在未来 3 年后等）
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 2.3.1 完成
- **风险等级**: 低
- **交付物**: `data_cleaner.py` 模块，输入脏数据 JSON → 输出干净数据 JSON，附带清洗日志（记录每条数据的处理动作）

### 2.4 数据同步机制

#### 2.4.1 同步策略设计

- **具体内容**: 确定各数据源的同步频率：E3/PLM 数据 → 每日全量同步（凌晨 2:00）+ 每小时增量同步（如有 API）；邮件数据 → 实时同步（新邮件到达即处理）；设计增量同步逻辑：基于 `updated_at` 时间戳或 E3 的变更日志（如有）；设计同步失败处理：失败重试（3次）→ 记录错误 → 发告警邮件 → 人工介入
- **天数**: 2天
- **角色**: 后端工程师
- **依赖**: 2.1 场景确认（API 场景可增量，CSV 场景只能全量）
- **风险等级**: 中
- **交付物**: 《数据同步策略文档》，包含各数据源同步频率、增量逻辑、失败处理流程

#### 2.4.2 同步任务实现

- **具体内容**: 使用 APScheduler 或 Celery Beat 实现定时同步任务；编写同步任务入口 `sync_job.py`：全量同步 → 清洗 → 入库；增量同步 → 清洗 → 对比差异 → 更新入库；记录同步元数据（最后同步时间、同步条数、失败条数）；配置同步任务的监控和告警
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 2.3.2 完成（清洗模块就绪）+ 2.4.1 完成（策略确定）+ 2.5 数据库就绪
- **风险等级**: 中
- **交付物**: 定时同步任务自动执行，同步日志可查，同步失败 5 分钟内收到告警

### 2.5 数据存储设计

#### 2.5.1 数据库选型确认

- **具体内容**: 评估并确认数据库选型：PostgreSQL（推荐，关系型+JSON 支持）vs MySQL vs MongoDB；确认公司现有数据库实例是否可复用；确认数据库连接方式和连接池配置
- **天数**: 1天
- **角色**: 后端工程师
- **依赖**: 1.2 完成（服务器环境就绪）
- **风险等级**: 低
- **交付物**: 数据库选型决定，PostgreSQL 15 实例已创建，可远程连接

#### 2.5.2 表结构设计

- **具体内容**: 设计并创建以下核心表：`projects`（项目主表：id、name、status、owner、start_date、end_date、source_system、source_id、created_at、updated_at）；`milestones`（里程碑表：id、project_id、name、due_date、actual_date、status、owner）；`risks`（风险表：id、project_id、description、severity、mitigation、owner）；`sync_logs`（同步日志表：id、source、sync_type、started_at、finished_at、record_count、status、error_message）；`users`（用户表：id、name、email、role、department）；编写 Alembic 迁移脚本，支持版本管理
- **天数**: 2天
- **角色**: 后端工程师
- **依赖**: 2.3.1 完成（字段映射表确定）
- **风险等级**: 低
- **交付物**: `alembic upgrade head` 执行成功，所有表已创建，`\dt` 可看到 5 张核心表

#### 2.5.3 数据索引与查询优化

- **具体内容**: 为高频查询字段创建索引：`projects.source_system`、`projects.status`、`projects.owner`、`milestones.project_id`、`milestones.due_date`；编写常用查询的 SQL 并验证执行计划（`EXPLAIN ANALYZE`）；确保项目列表查询 < 100ms（万级数据量）
- **天数**: 1天
- **角色**: 后端工程师
- **依赖**: 2.5.2 完成
- **风险等级**: 低
- **交付物**: 索引已创建，`EXPLAIN ANALYZE` 验证查询走索引，无全表扫描

**DATA 合计**: 7-14天 | 1-2人 | 风险极高 | 预计完成 5月26日-6月2日

## Step 3: AI引擎 — "有脑子想"（AI）

### 3.1 分析逻辑迁移（JS → Python）

#### 3.1.1 现有 JS 逻辑梳理

- **具体内容**: 从 `Auto-PM-UI-Design.html` 和 `AutoPM-Analysis.html` 中提取全部分析逻辑代码；梳理 3 层迭代分析的数据流：Layer 1 Eliminate（消除非瓶颈任务）→ Layer 2 Parallelize（识别可并行任务）→ Layer 3 Shorten（缩短关键路径）；梳理输入数据结构（哪些字段参与分析）和输出数据结构（分析结果格式）；输出《现有分析逻辑说明文档》
- **天数**: 1天
- **角色**: 后端工程师
- **依赖**: Step 2 部分完成（需了解数据结构，但不需等全部完成）
- **风险等级**: 低
- **交付物**: 《现有分析逻辑说明文档》，含数据流图、输入输出示例

#### 3.1.2 Python 版分析引擎编写

- **具体内容**: 编写 `analyzer.py` 模块，用 Python 重写 3 层迭代分析逻辑；保持与 JS 版本完全一致的算法逻辑（对比测试用同一输入数据，输出必须一致）；实现分析结果的数据结构定义（Pydantic Model）；编写单元测试：至少 5 组测试用例（含边界情况：空项目、单项目、全延期、无延期、循环依赖）
- **天数**: 3天
- **角色**: 后端工程师
- **依赖**: 3.1.1 完成
- **风险等级**: 低
- **交付物**: `analyzer.py` + 测试用例，`pytest` 全部通过，与 JS 版输出对比一致

### 3.2 LLM 集成

#### 3.2.1 LLM 选型与接入

- **具体内容**: 评估并选择 LLM 提供商：OpenAI GPT-4o / Azure OpenAI / Claude API / 国内通义千问（需考虑公司合规要求）；确认 API 调用方式和认证（API Key / Azure AD）；确认调用成本估算（每日分析量 × 每次 token 数 × 单价）；编写 LLM 调用封装模块 `llm_client.py`：统一接口、重试逻辑、超时处理、token 用量记录
- **天数**: 2天
- **角色**: 后端工程师
- **依赖**: 3.1.2 完成（需知道传什么给 LLM）
- **风险等级**: 中（公司可能限制使用外部 API；成本可能超预期）
- **交付物**: `llm_client.py` 模块，调用 LLM 返回结构化分析结果，token 用量已记录

#### 3.2.2 Prompt 工程与深度解读

- **具体内容**: 设计 LLM Prompt 模板：项目状态摘要生成（给定项目数据 → 输出 3 句话摘要）；延期根因分析（给定延期项目数据 → 输出可能原因 + 建议）；资源冲突检测（给定多人多项目数据 → 输出冲突点和建议）；编写 Prompt 测试集：10 个真实场景 + 期望输出方向；迭代优化 Prompt 直到输出质量稳定
- **天数**: 2天
- **角色**: 后端工程师 + PM（评审输出质量）
- **依赖**: 3.2.1 完成
- **风险等级**: 中（LLM 输出不稳定，需多轮调优）
- **交付物**: 3 套 Prompt 模板（摘要/根因/冲突），测试集 10 个场景输出质量评分 ≥ 7/10

### 3.3 定时任务调度

#### 3.3.1 分析任务调度器

- **具体内容**: 使用 Celery Beat 或 APScheduler 配置每日分析任务：每日 06:00 执行全量项目分析（数据同步完成后）；每日 07:00 执行 LLM 深度解读（分析完成后）；异常触发分析：数据同步检测到重大变更时立即触发；配置任务依赖链：同步 → 分析 → LLM解读 → 预警检测 → 通知发送
- **天数**: 2天
- **角色**: 后端工程师
- **依赖**: 3.1.2 完成 + 3.2.1 完成 + Step 2 数据同步就绪
- **风险等级**: 低
- **交付物**: 每日 06:00 自动执行分析，07:00 自动完成 LLM 解读，日志可查

### 3.4 预警规则引擎

#### 3.4.1 延期预警规则

- **具体内容**: 实现延期检测规则：规则 1 — 里程碑已过截止日但状态非完成 → 触发「延期预警」；规则 2 — 里程碑距截止日 ≤ 3 天且状态为未开始 → 触发「即将延期预警」；规则 3 — 项目整体进度落后于基准计划 ≥ 20% → 触发「严重延期预警」；输出格式：项目ID、预警级别（黄/橙/红）、延期天数、影响范围、建议动作
- **天数**: 1天
- **角色**: 后端工程师
- **依赖**: 3.1.2 完成（分析引擎可用）
- **风险等级**: 低
- **交付物**: `delay_detector.py` 模块，单元测试覆盖 3 条规则

#### 3.4.2 卡住预警规则

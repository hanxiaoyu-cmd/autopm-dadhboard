# 验收、任务交接与进度管理

版本：v1.1｜2026-09-11。适用 Airtable、微软工程及治理工作包。

## 1. 三种状态分开

| 维度 | 状态与用途 |
|---|---|
| 规划 | Defined：范围、依赖、输出和用例已定义；Change Pending：范围正在修订 |
| 执行 | Unassigned / In Progress / Waiting Dependencies / Blocked Environment / Submitted / Rework / Deferred |
| 验收 | Not Submitted / Under Review / Needs Rework / Accepted / Accepted with Follow-up |

本包全部工作包是 Defined，未向任何执行 AI 派发。Not Submitted 不等于尚无历史成果；历史成果只在候选资产中登记。Blocked Environment 只用于有事实依据的环境缺口，不掩盖代码缺陷。

Accepted 必须附审核编号、版本、环境、通过的用例和证据位置。Accepted with Follow-up 仅用于不影响本包承诺结果的轻微问题；数据丢失、越权、错误完成、重复业务对象、核心链路缺失不能用此状态通过。

## 2. 从派发到通过的固定流程

1. 协调方从任务主表选择已满足依赖的包，填写实际执行者、工作位置、目标环境和授权范围。一个 AI 先接一个有边界的工作包。
2. 执行者读取任务及指定资料。只检查本包的输入和消费者；历史证据漂移时报告具体差异，不重做无边界的全系统盘点。
3. 按包执行，记录版本与变更对象。阻塞时提交已完成部分及缺口；未运行的步骤写 Not Run，不能用预计行为填入实际结果。
4. 用 `templates/DELIVERY.md` 提交到 `submissions/<任务ID>/<提交版本>/`。文件留在共享目录或约定 Git 分支，用户不需要转述运行细节。
5. 本会话按 `templates/REVIEW.md` 核对成果、证据和目标，抽查关键结果。发现差异则返回具体条目、复现条件、预期结果及对应任务。
6. 本会话写入 `reviews/<审核编号>.md`，再更新任务主表及变更记录。执行者不能自行把审核状态改为 Accepted。
7. 生产发布属于 AT-11 / MS-10 的受控批次；组件通过不自动获得生产发布、真实发信或跨系统写回的授权。

这是后续采用的交接规程，本轮没有启动自动监控或向其他 AI 发消息。

## 3. 证据分层

| 等级 | 可以证明 | 不可以证明 |
|---|---|---|
| E0 设计／静态配置 | 方案、字段定义、脚本版本存在 | 实际运行正确 |
| E1 离线测试 | 固定输入下逻辑通过 | 平台权限、连接、触发和界面有效 |
| E2 平台组件测试 | 真实测试环境读写／原生公式／触发的指定行为 | 全链路和生产环境全部可用 |
| E3 完整链路与角色测试 | 指定环境、版本和角色完成业务结果 | 连续业务采用与收益 |
| E4 真实运行 | 两个周度周期的实际操作、异常处理和责任交接 | 未覆盖范围的自动完成 |

统计口径必须比较关联明细与平台原生计算。页面必须有实际浏览、操作、保存和重开读取证据。邮件队列、提供商接受、最终送达、用户处理分开记录；“发送成功”不能充当全部四层。

## 4. 每包通过的最低条件

- 任务承诺的输出齐全，代码／配置／文档版本与测试对应；变更列表无越界对象。
- 引用用例逐条有 Expected、Actual、Pass/Fail/Not Run、时间、角色和证据；模拟／合成／真实业务数据明确标识。
- 创建和更新均有独立读回；超时、重试及部分成功测试有可核对的结果。
- 已知失败按严重程度登记，回退方法考虑后续合法修改；不直接导入旧快照覆盖新记录。
- 执行者交付维护入口、参数位置和错误处理；团队入口包必须由非开发者实际操作。
- 依赖尚未满足时可以接收离线成果，但完整工作包仍不能标 Accepted。

## 5. 发布与运行门槛

**组件门槛**：每包规定用例通过，关键错误为零。**链路门槛**：建项目→计划→任务→SKU例外→Issue恢复与验证→周报／Tracker贯通，真实角色和并发测试通过。**运行门槛**：约20个XPT项目覆盖主要场景，两个连续周度周期，团队可独立维护。

约20个项目是业务试用范围；全量数据查询和迁移对账仍使用完整范围。没有真实 Issue 时保留未发生记录，不制造问题凑试用数量。上述周期不能用本轮离线测试替代。

Dataverse 环境审批、许可证、服务身份及后台连接未就绪时，微软任务可以完成离线设计／逻辑验证；发布门槛保持未满足。Airtable 与微软分别通过，不以一端通过替代另一端。

## 6. 进度怎样向 Sun Sun 汇报

固定只报告：本批要交付的业务能力、已接受成果、返工项、被阻塞的依赖、下一批可开始事项。需要数字时给出任务状态分布和覆盖用例数量，不能把135个Action历史Done数量换成产品完成率。

任务拆分变更保留旧ID并映射后继；规则变化记录 BR 编号、决策依据、受影响字段／任务／测试。评估时间分成执行投入、外部等待和业务观察周期；本包没有编造日历工期。
